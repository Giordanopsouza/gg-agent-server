# GitHub App connection (task 065)

The browser session comes from Supabase Auth (Google). A separate GitHub App user authorization links a verified numeric GitHub user ID to `auth.users.id`. Matching email addresses do not link identities or grant repository access. The `GET /user/installations` response made with that GitHub App user token is the only source for the connected user's installation list. A browser supplied `installation_id` is ignored. Task 066 will check a selected repository and mint its restricted installation token.

## App registration and secrets

Register a GitHub App with a callback URL at `GG_WEB_ORIGIN/auth/github/callback` and a webhook URL at the public runtime origin `/webhooks/github`. Route `/auth/*` to the runtime from the same browser origin in production; Vite proxies it locally. Set `GG_GITHUB_APP_CLIENT_ID`, `GG_GITHUB_APP_CLIENT_SECRET`, `GG_GITHUB_WEBHOOK_SECRET`, and a separate Fernet `GG_GITHUB_CONNECTION_KEY` on the runtime only. The app secret, webhook secret, cipher key, user token, and installation tokens never belong in the frontend. Keep `GG_WEB_COOKIE_KEY` and Supabase session settings configured as well. The App's **client ID** differs from its App ID. Keep “Request user authorization during installation” off: the connection begins at `/auth/github/start` with a session-bound state and PKCE verifier. The app's public install page can be offered after connection; installation callbacks by themselves grant no access.

For task 065, the GitHub App user authorization needs no extra account permission to call [`GET /user/installations`](https://docs.github.com/en/rest/apps/installations#list-app-installations-accessible-to-the-user-access-token). GitHub grants repository Metadata read automatically; task 066's repository read/write and PR flow will require Contents read/write and Pull requests read/write. Add permissions only when that flow is implemented and verify against [GitHub's permission guide](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app). An installation token acts as the **App**, so GitHub may attribute its Git and API operations to the App rather than the connecting user.

## HTTP contract

- `GET /auth/github/start` (signed-in browser): redirects to GitHub with random state and PKCE. The state hash is stored for ten minutes with the Supabase user UUID and active session UUID; the encrypted flow cookie is HttpOnly, Secure in production, and SameSite Lax.
- `GET /auth/github/callback?code=...&state=...`: consumes state once, verifies the same live Supabase session, exchanges the code server-side, checks `GET /user`, then lists installations. Returns to `/?github=connected` or `/?github=cancelled` without a token in the redirect. A GitHub identity already linked to a different app user returns 409.
- `GET /auth/github`: returns `{status, login, installations}` with `Cache-Control: no-store`. The list is refreshed through GitHub, so a removed installation is excluded. No token or email is returned. `pending` means GitHub currently lists no accessible installation (including an organization request awaiting approval); `revoked` means the user authorization needs reconnection. A transient GitHub failure returns 503 and does not grant cached access.
- `DELETE /auth/github`: requires the active session and exact `Origin`; it deletes the encrypted token and installation snapshots for that owner. This disconnects the account from this product; to revoke the GitHub App authorization at GitHub, use GitHub’s [authorized Apps settings](https://docs.github.com/en/apps/using-github-apps/reviewing-and-revoking-authorization-of-github-apps). Reconnect via `/auth/github/start`.
- `POST /webhooks/github`: validates `X-Hub-Signature-256` over the original bytes, stores `X-GitHub-Delivery` for deduplication, and invalidates on `installation.deleted`, `installation.suspend`, and `github_app_authorization.revoked`. The webhook does not grant access. A late invalidation may temporarily remove a snapshot; the next status read verifies against GitHub and restores an accessible installation. A late authorization revocation requires an explicit reconnect. Unknown events are only deduplicated.

GitHub user access tokens can expire. This implementation returns `revoked` on an expired or revoked token and asks the user to reconnect. In-flight operations that already received an installation token are outside task 065. Webhook receipts and expired flow rows need periodic retention cleanup after the task's retention policy is established.

## Validation

Automated HTTP tests use a controlled GitHub provider and cover forged state, another app account, replay, pending installation, disconnect, invalid signature, and duplicate delivery. The isolated local Postgres test covers encrypted token storage, RLS owner isolation, cross-account GitHub ID uniqueness, and webhook deduplication. For a real App check, configure a test App with the callback and webhook URLs, sign in through Google, visit `/auth/github/start`, install the App on a test account, check `/auth/github`, remove the installation, then revoke user authorization and reconnect. Do not require a paid installation for ordinary CI.
